# AI Monk Factoryのクラウド実装・原価契約

## 目的と範囲
Databaseの根拠を台本へ戻し、利用者がGoogle認証後に「monk avatarを生成 → 完成動画を最大3本無料で生成 → Instagramを接続」と進めるWeb appを作る。動画・台本・profileは既定値で生成し、promptや毎日の手動操作を求めない。Instagramを接続すると、無料動画枠または有効なsubscriptionがある間、日次生成・投稿を自動開始する。完成動画3本は期限なし・カードなしで提供し、3日trialは置かない。Instagramを先行し、TikTokは公開Content Posting API監査後に追加する。既定profileは任意で編集できる。web appを先に提供し、iPhone appは後続とする。既存の日次Grok所有loop、書籍決済は変更しない。公開mockやlocalhost planをSaaS完成と扱わない。

初回導線は「Google認証 → Generate Monk Avatar → Generate Full Video（最大3本無料） → Connect your IG to auto post」とする。Instagram接続はavatarと完成動画が1本以上できた後に許可する。Connect押下が明示的な自動投稿同意となり、Meta OAuthの公式readback後は残りの無料枠または有効subscriptionの範囲で日次生成・投稿を開始する。無料枠を全て使い切った後の接続も許可するが、Checkout完了まで自動生成・投稿は待機する。OAuth後の実投稿には対象accountの公式permissionとprovider設定が必要で、未確認なら生成と投稿のreadinessを分けて表示する。

Connect前のInstagram日次投稿は停止する。接続操作そのものが自動投稿の明示的な開始指示となる。未準備なら不足機能をボタン付近と画面内に示し、生成APIへ誤送信しない。利用者はいつでもPause/Stopでき、profile編集は任意とする。利用者から「ボタンが動かない」と報告があり、source reviewでMeta OAuth URLがUpload-Post host allowlistに拒否される不具合を見つけて専用branchで修正した。これはInstagram接続CTAのsource bugを直す変更であり、未設定runtimeのGenerate APIやproduction反映まで直った証明ではない。

## 採る方式と理由
既存Next/Netlify/Supabase/Stripeを使い、server-verified user IDへjob・billing・接続を結ぶ。画像/台本はGemini API、動画はHeyGen API、投稿はInstagram/TikTok公式APIを使う。接続時に各platformのOAuth同意を一度行い、その後の生成・投稿・metrics取得はserver APIで動かす。providerキーとOAuth tokenはserverだけが持つ。Instagramはprofessional Business/Creator accountとpublish scopeが必要で、新規連携はMeta公式Instagram API with Unified Loginを使う。Meta business app、`config_id`、HTTPS OAuth callback、Webhook endpointを設定し、`instagram_basic`/`instagram_content_publish` permissionを使う。日次投稿を継続するUnified Login設定ではtoken expiryを指定せず、Standard Access・app role/testerとexpiry設定をreadbackする。expiryを設定する場合は期限前のMeta token-management更新と必要permissionが実装・検証済みになるまで有効化しない。内部の`monk.mujo`検証ではStandard Accessとapp role/testerを使い、顧客向けAdvanced Access・Meta App Review・Business Verificationは外部提供前に完了する。OAuth tokenは暗号化してserver-sideだけへ保存し、clientやlogへ返さない。Page接続accountでPage Publishing Authorization (PPA)が要求された場合は利用者側で完了する。TikTokはregistered app、`video.publish`のapp承認と各userのOAuth認可、public posting用app auditが必要で、audit前の投稿はprivateに制限される。既存依存を再利用し、新frameworkや設定画面を増やさない。

旧local CLIをcloud経由で利用者へ公開する案はtenant認証と永続jobを持たず、Macの日次所有系を巻き込むため採らない。Postiz通常APIの接続先は自社organizationであり、tenant帰属の正式契約が不足する。Postiz Enterpriseは公開ページで新規申請停止のため採らない。Upload-Post Professionalは月USD50で25 profilesの容量上限があるため、成長時の顧客接続基盤として採用しない。既存実装は移行元とし、販売前に公式Instagram/TikTok APIへ接続を移す。Instagramの一度限りのOAuth認可は必要だが、日々の投稿に人の操作を求めない。

## Database Plugin/CLIとの接続
Factory Web appを先に提供し、tenant認証付きAPIが稼働した後に、既存CLI/Pluginから自動運転の作成・停止、生成job状態とmetrics取得を追加する。SNS tokenはserver側に保持する。host上でOAuth同意を完結できない場合は、Factory Webの一度限りのOAuth画面へ誘導する。利用者が同意した後の日次生成・投稿・metrics取得はAPIで実行し、毎日の手動操作を要求しない。この連携はFactory Web公開を止める前提ではない。

## ローンチ後の改善と配信
初回Factoryローンチは実E2E受入後にXへ一度だけ行う。継続するDatabase調査、Factory product iteration、X配信は、親field guideの「継続改善・配信ループ」に従う。内部改善loopは有限runとしてDesktop Scheduled Tasks/既存heartbeatから起動し、顧客ごとの自動生成jobとは分ける。Grok Bot所有の日次IG/TikTok投稿を再スケジュール・再送しない。1runごとに出典・変更・検証・provider receiptを保存し、確かな改善材料がない場合は何も投稿せず終了する。

## 最小の利用導線
利用者はGoogle/Supabase login後にGenerate Monk Avatarを押し、次にGenerate Full Videoを最大3回まで無料で使う。少なくとも1本の完成動画をpreviewした後にConnect your IG to auto postを押す。OAuth callbackでaccount IDとpublish permissionを確認すると、無料枠が残るかsubscriptionが有効なら、追加設定なしで日次jobを開始する。無料枠を使い切った後はCheckoutが必要で、接続済みintentは支払確認後に日次jobを自動開始する。profileは任意編集とし、完成video previewを表示する。

Instagramはprofessional Business/Creator accountを接続する。OAuthから戻っただけではconnectedにせず、公式APIでaccount IDとpublish権限を確認する。Connectが自動投稿の明示的な同意であり、free allowanceまたは有料subscriptionが有効なら1日1本を既定時刻に制作・投稿する。枠を使い切りsubscriptionが無い場合は接続済み状態で待ち、Checkout完了後に自動再開する。停止・解約・認可失効は次回の生成/投稿を止める。利用者はmonk profileを編集できるが、投稿先・script・scheduleや日々のGenerate操作は要求しない。TikTokは公式app audit後に同じ最小導線へ追加する。

dashboardは実provider状態、投稿URL、取得日時付きのviews/likes等を表示し、未取得を0にしない。投稿直後にInsightsが空でも動画jobは完了し、status refreshで最古の古い投稿metricsを1件だけ再取得する。成功値が12時間以内なら再照会せず、失敗後も15分以内は再試行しない。無料枠の残り（3本からの減算）、有料月間の残数、次回投稿、subscription状態、Pause/Stopを簡潔に表示する。動画とcaptionはAI生成であることを明示する。

## 実装の境界
- 現在の公開draft入口を同じURLの実Web appへ置き換える。localhost向け4file配布はdownload用pathへ移し、public staticとNext routeを衝突させない。既存利用者や永続draft移行の要件は確認されていないので互換レイヤーを増やさない。
- 無料quotaは認証userごとに完成動画3本の生涯枠とし、時間経過でresetしない。Stripe trial fieldsは使わない。有料quotaは公式paid invoice期間に紐づけ、paid30成功/最大36attemptを繰越0で管理する。費用不明の試行は原価予約を保持し、公式に非課金と確認できたものだけ解放する。
- readinessは共通booleanへ集約せず、generation・checkout・socialをaction別に返す。core runtime flag/job secretが不足する場合はjobを停止し、provider設定不足は生成を、Stripe設定不足はcheckoutを、公式OAuth/publish設定不足はsocial actionだけを止める。clientへsecretや内部env値を返さず、なぜ操作できないかを利用者向けの安全なstatusで表示する。readinessがfalseでも該当CTAはクリックでき、押下時は安全な理由を画面内に表示するだけにする（API POST・job作成・quota/attempt消費は行わない）。Instagram接続はgenerationとsocialの両方がreadyで、avatarと完成videoがある場合だけAPIへ進める。無料quotaが不明な場合は残数0と区別し、課金導線を出さずstatus更新を案内する。OAuth接続は3本のfree quotaを使い切っても許可し、autopostはquotaまたはsubscriptionが使えるまで待つ。
- Netlify APIはSupabase server getUserでbearerを検証する。client入力user_id/customer_id/profileを信用しない。RLSは自分のrowの読取だけ、課金/生成/接続の更新はserver限定とする。
- account/job/provider-eventを永続化する。unique occurrence/lease、atomic count/seconds/USD予約で連打・並列・scheduled再実行の二重効果を防ぐ。timeout後のeffect不明は予約を保持し、公式GETで照合する。
- 全利用者のgeneration job予約を共有する会社上限をUSD10/UTC日で開始する。無料1人分の予約USD4.18（avatar USD1.60 + video 3本 USD0.86）を基準に、2人分USD8.36とUSD1.64の余裕を置く。DB予約transactionで同時実行を直列化し、当日作成されたjob、当日更新されたgeneration-stage job、過去日の未解決 `reserved`/`processing`/`effect_unknown` generation jobを合算してからmanual/auto双方のjobを許可する。social `post_*` stageはgeneration費を使わないため別枠とする。上限は実provider請求額ではなく、現在のmodel/usage前提に基づく予約costの上限であり、price change前に予約額と上限を更新する。
- 先にspeechを生成し公式durationを読んでからAvatar IVへ渡す。単語数から秒数を保証しない。上限超過の短文化は残予算内だけで行い、音声が上限を満たさなければ動画生成しない。
- Stripe Checkoutは固定server Price、mode subscription、server user IDをmetadataへ保存する。無料quota中はcheckout/cardを要求せず、quotaを使い切った後にだけcheckoutを表示・許可する。subscription作成にtrial_period_daysやtrial fieldsを含めない。webhookはraw署名・event一意性・公式subscription再取得で利用権を更新し、success URLだけから有料化しない。portalは認証済み本人のcustomerだけを使う。
- Checkoutのnonce/作成時刻/公式session IDを永続化し、通信失敗後も同じStripe idempotency keyとpayloadを使う。期限後に結果不明のsessionを別nonceで再作成しない。課金状態の同期は利用者ごとの期限付きnonceで排他し、公式GET前に取得したnonceが一致する場合だけ更新する。有料期間はsubscription itemの公式periodと同じ期間のpaid invoice lineで確定し、古いinvoiceだけで次月を有効化しない。解約予定も次の有料生成/自動投稿を止める。
- 同一Stripe accountの既存webhookへFactory eventが届いても、別商品のdropletやwake-callを作らない。広いsubscription受付を持つ既存2handlerはFactoryのproduct IDだけを除外し、既存商品の契約を変えない。
- platform OAuth tokenはserver側で暗号化し、各user/accountに限定して保存する。stateは一回限り・期限付きとし、OAuth callbackでaccount ID/permissionsを公式readbackしてから接続完了にする。投稿・metricsも公式GET/POSTで状態を確定する。OAuth開始前にdaily automationへの明示意思を永続化し、公式接続readback後だけ開始する。停止はautomation stateとpending intentを一操作で消し、後続OAuth readbackが勝手に再有効化しない。別userのtoken/accountへアクセスできないtenant境界を維持し、Grok Bot所有の日次処理を変更しない。Instagram/TikTok公式審査が未完なら顧客向け公開投稿を有効化しない。投稿APIがtimeoutした場合はeffectをunknownとして保持し、公式readbackが解決するまで再送しない。
- 非同期生成と投稿は永続jobを短いscheduled tickで進める。新schedulerやMac常駐processを作らず、利用者向けAPI request中に長時間待たない。同期画像生成APIだけは既存Netlifyのbackground functionを使う経路を検証し、DBの所有権と送信前fenceを取得した最初の1回だけproviderへ送る。自動retryは当該fenceを読んで再送せず、費用不明は予約を保持する。submit→provider ID保存→next_run_at付きpollへ分け、1tickの件数/時間を上限で止める。既存CLIの--waitやbackground functionの自動retryをそのまま移植しない。各効果はprovider ID/official readback/費用/次の操作を持つ。
- Factory専用の独立billing sourceを使い、Grok key/walletへのfallbackは0とする。shared Grok walletやAPI残高を利用者quotaの代わりにしない。walletのauto-reload設定は変更せず、既存threshold guardと利用者/全体予算を守る。Factory用の支払元・使用可能予算が足りなければ生成前に具体的な不足を表示し、成功へ置換しない。
- API key・OAuth JWT・webhook secretはprivate SSOTとdeployment secretsだけで扱い、client/repo/logへ出さない。
- 生涯無料artifact数とsocial接続容量を分けて永続化する。subscriptionのcancel/expirationはpaid生成・次回投稿を止めるが、無料artifact履歴と実費を消去しない。完了済み動画数は成功したartifactだけを数え、timeout後の不明なprovider費用・投稿はreceipt/readbackで確定するまで再送しない。
- 定期tickはStripe SDKを含む全通信へ共通25秒の打切りを適用し、Netlifyの30秒上限より先に終了する。Stripe Price/portal/webhook secret/live-modeが欠ける間はcheckoutを停止し、generation readinessを誤ってfalseにしない。provider key/model accessが欠ける間は生成だけを停止する。状態取得が失敗した場合も、本人認証後の停止操作は課金同期を通さず利用できる。

## 完了条件と実行順
1. 原価表、価格/回数/秒数、本人確認とjob/接続/課金契約を正本へ先にcommit/pushする。
2. 関係する最小の失敗テストを先に確認し、auth/tenant隔離・quota同時予約・Stripe署名/重複・OAuth帰属・job再実行を実装する。関連検証とsource review/CIを通す。
3. 最新mainへ統合し、必要なprovider/deployment設定を対象限定で反映する。実login/3本無料枠/有料subscription/本人OAuth接続/独自avatar・video/公式投稿・metricsを実receiptと分けて確認する。
4. 実利用できる状態をXで告知する。売上・MRR・他者利益・正式directory掲載は、対応する外部結果が無い限り未達とする。
