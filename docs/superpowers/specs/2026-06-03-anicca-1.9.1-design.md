## 1. Overview (What & Why)

### What
Anicca iOS 1.9.1 を 1 リリースで App Store に提出し「Waiting for Review」へ。 7 項目すべて 1.9.1 同梱 (分割しない — Dais 2026-06-03 厳命):

| # | 項目 | 種類 |
|---|------|------|
| ① | iOS PushTokenService.register 経路 修復 (1.9.0 後 register 0 件 = 真因) | iOS hotfix |
| ② | main repo source を affirmation sender 版 に統一 (production runtime と整合) | backend source |
| ③ | billing-issue 銀河 banner (involuntary churn 回収 / Feed 上部) | iOS UI |
| ④ | 通知タップ↔カード cold-start race fix (pendingQuoteId) | iOS |
| ⑤ | JA affirmation 12 件 → 自然な日本語 | content |
| ⑥ | Settings 「毎朝のメールを受け取る」 (UI + endpoint + Resend Segment + daily Broadcast cron) | iOS UI + backend full pipeline |
| ⑦ | Settings 「ご意見・改善要望」 (UI + endpoint + Resend → Dais) | iOS UI + backend |

### Why (real DB evidence embedded)

**APNs 通知 4 日停止 の 真の真因 (psql で 直接確認 = circular でない evidence):**

```
push_tokens テーブル (production DB direct query, 2026-06-03 22:55 JST):
  total          = 608
  active         = 118  (disabled_at IS NULL)
  disabled       = 490
  last_error 内訳: Unregistered 450 / BadDeviceToken 40 / NULL 118
  week_new (直近 7 日 register 件数) = 0 件 ★
```

```
log evidence (Railway API service, 同 timestamp):
  [WARN] [AffirmationApnsSenderJob] APNs send failed: Unregistered  (全 fan-out で同一)
```

```
解釈:
  - 1.9.0 release (2026-05-29) 後の 5 日間で 新 token register = ★ 0 件 ★
  - 既 active 118 token は 5/26 以前 (= 1.8.6 build 起源)
  - 1.9.0 install で iOS が APNs token を rotation → 旧 token を Apple が無効化
  - backend は 旧 token で 送信 → 全 Unregistered
  - 真因 = iOS 1.9.0 build で PushTokenService.register が呼ばれていない
    (didRegisterForRemoteNotificationsWithDeviceToken に到達せず、 backend
     POST /push-tokens に新 token が届かないループ)
```

その他の実害:

| 問題 | 影響 | 出典 |
|------|------|------|
| MRR $60 → $20 / install/日 ≒ 0 | 事業 危機 | Dais 2026-06-03 |
| 通知タップで 別カード (cold-start race) | "ペア性" 信頼失墜 | FeedRootView.onReceive が subscribe 前 post (前 session 診断) |
| billing 失敗 silent churn | $RCA…5cc4 が grace_period 放置 | RC dashboard (前 session) |
| JA 12 件 直訳臭 | retention 核 | 前 session 200 件 audit |
| email retention loop 不在 | re-engage 経路ゼロ | Settings コード確認 |
| in-app feedback 不在 | App Store review 以外 声届かず | Settings コード確認 |

## 3. As-Is / To-Be

### ① iOS PushTokenService.register 経路 修復 (★ 真因 ★)

| | As-Is (DB evidence) | To-Be |
|---|---------------------|-------|
| 直近 7 日 新規 register | 0 件 | 1.9.1 install ユーザの新 token が register される (24h で >= 10 件) |
| 既存 active token (118 個 / 5/26 以前) | 古 token、 Apple 側で Unregistered 扱い | 新 register で置換、 disabled へ自然遷移 |
| iOS 修復 (実装方針) | `AppDelegate.application(_:didFinishLaunchingWithOptions:)` は `UIApplication.shared.registerForRemoteNotifications()` を呼ぶ既存実装 (前 session 確認済)、 ただし 1.9.0 build で **本当に呼ばれているか** が未確認 | (a) `didFinishLaunching` 内 register 呼出 を MUST、 (b) `applicationDidBecomeActive` でも MUST 再 register (idempotent、 token rotation 即時 catch)、 (c) `didRegisterForRemoteNotifications` callback で `PushTokenService.register(deviceToken: token)` を MUST 呼ぶ、 (d) `PushTokenService.register` の HTTP 失敗時 (network / 4xx / 5xx) は 3 retry + exponential backoff、 最終失敗を `os_log` ERROR + UserDefaults flag set (次起動 再試行) |
| backend cooldown 戦略 (副) | `Unregistered` 受信 → 即 `disabled_at = NOW()` | 即 disable はそのまま (production 影響回避)、 ただし `last_error` を 'Unregistered' で記録し 7 日経過後に **強制再 register prompt 通知 1 本送信** (= 寝てる古 token user に "再起動してね" 通知)。 → ただしこれは 1.9.2 へ。 1.9.1 では cooldown 変更なし |
| 検証 | — | DB query で 1.9.1 release 後 24h 以内に新 token >= 10 件 register、 かつ `sent ok` >= 20 行 |
