# Anicca 1.8.7 — Affirmation Notifications + i18n Spec

**Status:** Draft (pending Dais approval)
**Branch:** `feature/iam-feed-app-redesign` → merge to `release/1.8.7`
**Scope:** 通知体験の全面刷新 + Spanish localization + 旧 Railway push 廃止戦略

---

## 0. なぜこの spec か

旧 1.8.6 までは「悩み別 LLM 生成 nudge を Railway → APNs」で配信。1.8.7 の feed リデザインに合わせて通知体験も書き換える:

- **Title**: `アニッチャ` / `Anicca` (アプリ名のみ。問題別タイトル廃止)
- **Body**: `QuoteProvider` の curated 60-pool からランダム
- **Tap**: 該当 quote の card に main feed が直接スクロール (NudgeCard ポップアップ廃止)
- **言語**: EN / JA / ES の 3 言語対応 (DE / FR / pt-BR は EN プールにフォールバック)

## 3. ランダム rotation 戦略

**問題**: 毎日同じ quote が来たらユーザが秒で uninstall する。日替り + 60 日重複なし + 端末ごとに違うシードが必要。

### アルゴリズム

```swift
// QuoteProvider.todayNotificationIds(count:preferredLanguage:date:calendar:)
1. installSeed = UserDefaults.standard.integer(forKey: "anicca.shuffleSeed")
   ← 初回起動時に Int.random(in: 0..<1_000_000) を保存。端末ごとに違う。

2. cycle = floor(daysSinceInstall / 60)  // 0, 1, 2, ...
3. seed  = installSeed ^ cycle           // サイクルごとに新シャッフル
4. shuffled = pool.shuffled(using: SeededGenerator(seed))
5. dayInCycle = daysSinceInstall % 60    // 0..59
6. slotIndex  = dayInCycle * count + 通知 slot index
7. return shuffled[slotIndex % pool.count]
```

これで:
- 端末 A と端末 B は **完全に違う順序** (installSeed 異なる)
- 同じ端末で 60 日経過するまで **同じ quote は絶対来ない**
- 60 日サイクルの境界で **別の順序に再シャッフル**
- Pool 全 60 個を保証的に使い切る

**現状の `todayNotificationIds` は day-of-year ベースで全端末同期 + 周期 60 日固定** → これでは不十分。spec 通りに書き換える。

## 4. Remote vs Local — 最終決定

### 比較 (新文脈: 「今すぐ Railway 停止は service 中断、1.8.7 リリース後にゆっくり」)

| 観点 | Remote (Railway 継続) | Local (新規実装) |
|------|---------------------|-----------------|
| 1.8.6 残存ユーザへの service 継続 | ◎ 旧 push 来続ける | × アップデートまで通知無し |
| 1.8.7 アップデート後の体験 | サーバから新 payload 送れば変えられる | アプリ bundle 内 quote から発火 |
| App Store 通さず content 更新 | ◎ サーバ deploy だけ | × app update 必須 |
| 60 個ランダム rotation 実装コスト | サーバ DB + cron logic 改修 | 端末 1 ファイル (`QuoteProvider`) |
| 多言語 (EN/JA/ES) | サーバ i18n 実装必要 | `Locale` 自動 |
| Offline 配信 | × | ◎ |
| サーバ infra コスト | $20-40/月 (Railway + APNs) | $0 |
| 二重通知防止 | サーバ側 dedupe + version gate 必要 | 端末側のみで完結 (旧 token を unregister) |
| 業界慣習 (i.am / Mantra / Calm 等) | ほとんど local | local 採用 |

### 推奨 — **ハイブリッド (フェーズ展開)**

**Phase 1 — 1.8.7 リリース直後 (Day 0-30):**
- iOS 1.8.7 client = **ローカル通知のみで動く** (`AffirmationNotificationScheduler` 完全実装)
- 1.8.7 起動時に **`unregisterForRemoteNotifications()`** + `PushTokenService.markUnregistered()` を 1 回だけ実行
  → Railway 側で token 自動失効 → APNs 配信対象から除外
- Railway 側 **`problemNudgeApnsSenderJob.js` は稼働継続** (1.8.6 残存ユーザのため)
- 1.8.7 client の `userNotificationCenter(_:didReceive:)` で `messageId` 入りの payload は **return** (受信した場合表示しない、defense in depth)

**Phase 2 — 1.8.7 普及完了後 (Day 30-60):**
- iOS App Store の自動アップデートで 1.8.7 普及率が 95%+ に達した時点
- Railway 側 `problemNudgeApnsSenderJob` の cron を **disable**
- Server-side で `appVersionSemver < '1.8.7'` の token 削除

**判断ポイント**:
- 1.8.7 リリース当日 = Railway 触らない (壊さない)
- 1.8.7 普及後 = Railway 停止

→ **service 中断ゼロ、二重通知ゼロ**
